# 架构与代码质量规则

## 架构与边界

- 保持既有架构和模块边界, 禁循环或逆向引用. 依赖遵循项目声明方向; 未声明则单向. 必须改变时先说明影响, 由用户决策.
- 跨模块只经公开 API, DTO 或事件; 禁访问对方内部状态, 私有存储或实现细节.
- 共享抽象须有至少两处稳定需求; 单点不提前抽象. 禁为方便穿透层级, 复制领域逻辑或建全局可变状态.
- 改公共接口, 跨模块数据模型或依赖图前, 列影响模块和兼容方案.
- 删或合并模块前, 确认调用方已清退, 迁移路径与回滚风险.

## 代码质量

- 保证正确, 可读, 可维护.
- 性能优化须有测量或瓶颈证据.
- 函数和类型单一职责.
- 命名表达业务意图, 禁含糊缩写或无意义通用名.
- 边界校验输入, 处理空值与异常.
- 禁吞错误, 静默降级或用默认值掩盖失败.
- 资源, 并发, 取消须明确所有权和生命周期, 避免泄漏, 竞态, 无界重试或队列.
- 日志和错误信息禁泄露凭据, 个人数据或内部敏感信息.
- 测试覆盖直接影响的行为, 失败路径和回归点, 验证契约.
- 沿用项目格式化, lint, 错误处理和日志规范; 禁无说明地禁用检查或压低告警.
- 复杂判断注释说明原因, 不逐行复述. 临时代码本任务移除或明确隔离.

## 交付自检

卡片移入 `review/` 或单卡请求审核之前, 执行下列清单, 并把每项结果连同命令及其输出记录在 `IMPLEMENTATION` 下. 审核模块适用时, Reviewer 在任一类别发现问题即视为跳过了自检: 在卡片上记录为自检失败, 并与其他 finding 在同一修复轮次中修正. 这类 finding 仍是按 `KANDER-REVIEW-RULES.md` 处理的普通审核 finding: 第 3 到 5 项属于 `[mechanical]` 类别, 由机械证据关闭而不重跑 Reviewer, 其余走正常的修复与增量重审路径. 不存在单独的「不经审核退回」路径, 自检失败也绝不计为额外的审核轮次.

1. `git diff --check` 干净; 没有遗留冲突标记、行尾空白或文件末尾漂移.
2. 本次交付新增的非生成代码文件没有超过 1000 物理行的; 触及的文件中, 基线时不超过 1000 行的现在也不超过 1000 行; 原本已超过 1000 行的触及文件净增为零, 仅替换 import、适配器或胶水代码的改动除外.
3. 描述被改行为的注释与文档在同一 diff 内更新; 没有注释声称代码已不再具备的行为.
4. 没有死代码: 没有新增或遗留任何不可达、未调用或未引用的内容.
5. 没有冗余测试: 同一行为不重复覆盖, 没有与被测行为无关的断言.
6. 触及的模块能编译, 针对被改行为的定向测试确实在最终交付 commit 上运行过; 在结果旁注明该 commit. 最后一次代码改动之前产生的证据已过期, 必须重跑.
7. 声称「全部测试通过」须写明命令、commit 与数量; 缺任一项视为未执行.

## 验证记录

- 运行能直接证明改动的最小验证.
- 测试或环境失败记录实际命令与错误, 禁标通过; 既有环境故障同理.
- 敏感值替换为 `[REDACTED]`, 其余错误文本原样保留.
