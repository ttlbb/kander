# 任务组编排规则

仅在 `rules.task_groups=true` 且 `rules.git=true` 时启用任务组编排. 优先级与加载流程见 `KANDER-AGENTS.md`.

任务组固定用 `KANDER-GIT-RULES.md` 规则, 不支持关闭 Git 后自定义组集成契约.

- 先读取已启用的 `KANDER-GIT-RULES.md` 和命令协议 `KANDER-KANBAN-RULES.md`. 若配置不满足依赖, 保留卡片和工作区, 报告需调整的开关.
- 无 `origin` 或用户明确要求仅本地时, 跳过本文所有 push 和远端分支清理, 如实报告未同步远端.
- 编排计划须写明任务分支交付到组分支、各组按依赖顺序合回 `develop` 的步骤. 集成授权按 `KANDER-GIT-RULES.md`「集成与清理」执行; 已确认的计划明确包含这些步骤时不重复询问, 仅启动卡片不视为集成授权.

- 审核批次、finding 派回和审核门禁仅在 `rules.review=true` 或用户明确要求本次完整审核时适用.

  否则不加载 `KANDER-REVIEW-RULES.md`, 实现与验证完成后进入组集成流程, 仍须满足集成授权和项目交付门禁; 审核记 N/A, 不建立审核 base 链.

- 面向用户的固定报告格式仅在 `rules.reporting=true` 时读取 `KANDER-REPORTING-RULES.md`. 关闭时如实汇报进度、交付与未处理事项即可, 卡片内部记录和状态门禁仍然适用.
- 外部依赖进入 done 后还须确认其交付确实可用于当前组分支; 使用用户自有 Git 流程完成的单卡不保证改动已在 develop. 无法确认时报告实际缺口, 不自动替它合回.

## 任务 ID

- 任务 ID 为 `YYYYMMDD-short-slug-task`, 全看板唯一; 小卡去掉 `.md` 的入口名、大卡目录名即任务 ID.
- `short-slug` 由小写 ASCII 字母、数字及分隔它们的连字符组成, 不以连字符开头或结尾, 不含连续连字符.

## 任务拆分与任务组

- 除非用户明确要求保留单卡, 否则尽量将任务拆为可独立验收的小卡. 即使整体只有一个目标, 也应检查能否拆出可独立验收的子目标; 无法继续独立验收时停止拆分, 不为凑数量强拆.
- 每张卡聚焦一个可独立验收的小目标, 写明 `EXPECTED_OUTCOME` 与 `ACCEPTANCE_CRITERIA`.

- 目标拆分为多个任务卡时:
  - 这些任务卡构成一个任务组.
  - 通常任务组建议不超过 3 个任务卡.
  - 如果任务组超过 5 个任务卡, 尝试进一步拆分为多个任务组; 数量是建议, 不代替目标与依赖判断.
  - 任务组 ID 为 `YYYYMMDD-short-slug-group`, 全看板唯一.
  - 每张成员卡的 `- TASK_GROUP:` 元数据填所属组 ID, 非成员留空. 任务组是卡片关系, 不新增看板入口或状态.
  - 同一组的成员卡共用同一 `LANGUAGE`; 用相同的 `--language` 或在相同配置下创建.

- 优先拆为小卡; 无法继续拆成可独立验收的小卡且确需大卡时, 按 `KANDER-KANBAN-RULES.md`「任务规模与分组」选 SIZE. 共享接口或数据契约先明确, 需要独立交付时建契约卡作为前置.
- 建组时列全成员与依赖图, 排除缺失引用、依赖环和职责重叠; 进入 `todo/` 后按看板协议冻结任务组关系. 旧卡在 `DISCUSSION` 中记录的 `任务组: ...` 继续兼容, 不要求批量改写.
- 成员卡创建后逐卡完成 `KANDER-KANBAN-RULES.md`「建卡后自审」(成员卡属组, 须同时取得独立审卡的 `CARD_REVIEW:` 记录; 同一独立 Agent 可一次审整组), 再检查整组是否完整覆盖用户目标、卡间边界是否重叠或遗漏、前置交付是否满足后续卡的约束与验收. 发现问题先修正并复核, 通过后才推进到 `todo/`.

## 任务卡之间的依赖关系

- 组内卡对任务卡或任务组的依赖, 写在该卡 `DISCUSSION` 开头的独立代码块中. 字段名必须为 `PREREQUISITES`, 使用 ASCII 逗号分隔 ID, 可混写卡 ID 与组 ID:

```text
PREREQUISITES: 20260905-contract-task,20260905-foundation-group
```

- 无依赖时使用同一位置和代码块格式:

```text
PREREQUISITES: N/A
```

- 旧卡缺少该行时视为无依赖. 组引用展开该组当前全部成员, 不允许引用本组或形成跨组依赖环.
- 组内前置卡须到 `review/` 或 `done/`, 且主控已确认其最新交付 commit 包含在当前组分支中, 才满足依赖; 不能仅凭 `review/` 状态放行.
- 组外卡及组引用展开的全部成员须到 `done/`, 并确认其交付在当前 `develop` 可用. 非组卡不启用上述自动依赖解析契约, 其交付前提由执行 Agent 按任务契约核对.

## 并行执行任务卡

- 如果存在可以并行执行的任务卡, 要特别注明.
- 仅同时就绪且修改资源可隔离的卡并行; 同一资源无法隔离时记录依赖并串行, 不共享执行 worktree.

## Git 分支和 worktree

- 单卡由执行 Agent 按 Git 分册创建专属任务分支和 `<仓库根目录>/worktrees/<task-name>/` worktree, 源分支为 `develop`.
- 任务组使用两层隔离: 主控持有组分支 `group/<task-group-id>` 及 `<仓库根目录>/worktrees/<task-group-id>/` 专属 worktree, 用于接收交付、组级验证、适用审核及最终集成; 每张成员卡仍由执行 Agent 创建自己的任务分支和 worktree.
- 组内任务分支从最新组分支创建, 源分支为 `group/<task-group-id>`, 不从 `develop` 创建. 远端路径先 fetch `origin/group/<task-group-id>`; 其他分支命名、路径和用户改动保护要求沿用 Git 分册.
- 执行 Agent 只改本卡 worktree, 主控只操作组 worktree 和集成目标. 执行 Agent 的 rebase 与冲突修复在本卡工作区完成; 主控不代改任务分支或代码.

## 组集成分支

**创建与复用**

- 主控先按「启动与订阅」确认全组外部依赖, 并按 Git 分册初始化 `main`、`develop`. 外部依赖全部满足后, 在首卡启动前创建组分支与组 worktree.
- 有 `origin` 且非仅本地时 fetch, 从最新 `origin/develop` 创建并普通 push: `git push -u origin group/<task-group-id>`. 否则从最新本地 `develop` 创建并报告未同步远端. fetch 或创建失败时保留现场, 不启动成员卡.
- 记录组分支、组 worktree 路径及创建所用 `develop` 完整 SHA. 该 SHA 是创建锚点, 仅在审核适用时兼作首批审核 base. 恢复编排时核对并复用既有组现场与记录, 不覆盖分支或重新生成锚点.
- 最终集成前不 rebase 组分支, 不改写已交付的组历史. 适用审核批次的 base 链按审核分册维护.

**任务分支交付到组分支**

- 执行 Agent 实现、验证、按关注点提交后, 将本卡任务分支 rebase 到最新组分支并重新验证, 按 Git 分册更新任务分支. 在 `IMPLEMENTATION` 记录任务分支最终完整 SHA、所基于的组分支 SHA 和验证结果, 再 `move review` 并结束本轮响应. 执行 Agent 不更新组分支.
- 主控收到 `review/` 状态后读取交付记录, 核对集成授权及任务分支头与记录的最终 commit 一致. 远端路径先 fetch 并核对远端分支, 本地路径核对本地分支. 按 Git 分册「直接集成与 PR」将该 commit 交付到组分支并同步组 worktree; 远端路径先 push 最终 commit, 成功后才 ff 本地组分支. 已包含同一交付 commit 时只核对和同步, 不重复集成. 未获授权时保留 `review/` 与现场并报告, 不放行依赖.
- 组分支先前已前进、任务分支不能 ff 时, 主控只调用一次 `kander notify <task-id> --message-file <同步要求>` 派原执行 Agent rebase、解决冲突并重验. 主控不改本卡 worktree 或 commit; `notify` 非零时停止并报告. 新交付回到 `review/` 后重新核对, 不沿用旧交付结论.
- 主控确认本卡最新交付 commit 已在实际本地或远端组分支中, 且组 worktree 已同步到该头后, 才将本卡纳入待审核集合或放行直接后继卡. push、ff 或核对失败时保留 `review/` 和现场, 不放行依赖. 组分支出现非预期改动或分叉时报告, 不覆盖远端或重写已审核历史.
- 交付由主控串行接收, 不生成 merge commit. 审核适用时先安排批次再接收交付, 每批覆盖其 base 至本批 HEAD 的全部未审核交付, 不将批外改动混入组分支. 本批完成前其他 `review/` 卡排队; 批内修复在 Reviewer 退出后接收, 再复审, 保证审核对象与批次契约一致. 审核不适用时按依赖顺序直接接收.

**拓扑冻结**

- 本组任一审核批次未关闭期间, 主控不重新拆分本组、不在组间移动卡片、不更改卡片 owner、不接受契约变更. 用户提出上述任一要求时, 先关闭未关闭的批次 (通过, 或连同证据把该轮记为放弃), 再应用变更, 再开启新批次. 在批次中途应用此类变更会使该批次失效, 必须作为浪费的轮次报告, 不得默默吸收.

**合回与清理前置**

- 每组全部交付已进组分支、全部成员到 `review/` 且适用审核完成后, 主控按 Git 分册「集成与清理」检查集成授权, rebase 最新 `develop`、重新验证并合回. 同一编排中的后继组按此前置组的 `done/` 与实际交付解锁, 不等待所有组完成才集成.
- 主控记录集成前后组 HEAD 及各卡 commit 对应. `develop` 前进时沿用一次性审核门; 实质代码冲突用 `notify` 派原执行 Agent 处理, 主控不代修, 修复后的结果按适用审核重审.
- 清理前确认最终组改动已进入实际本地或远端 `develop`: 直接集成用 rebase 后的组 HEAD 核对 `git merge-base --is-ancestor`; 用户或项目要求 PR 时按 Git 分册的 PR merged 判据. 未满足则保留组与任务现场并报告.
- 满足后按「集成与收尾」派原执行 Agent 清理本卡现场. 全组卡片进入 `done/` 后, 主控移除组 worktree、本地组分支及适用的远端组分支; 失败只保留尚存现场, 不回退已完成卡.

## 任务编排

- 对于只有单个任务卡的任务:

  - 启动、手工领取及不同 launcher 的跟踪责任按 `KANDER-KANBAN-RULES.md`「领取, 启动与协调」执行.
  - 执行任务卡的 Agent 称为执行 Agent, 负责核对交付前提、创建专属 worktree、实现、验证和适用审核, 并按已获授权集成回源分支. 未获集成授权或交付门禁未满足时保留 `working/`, 记录待处理事项并报告.

- 对于任务组:

  - 当前 Agent 转为主控 Agent, 按依赖调度所有组和卡, 每组满足门禁后按已获授权集成并收尾, 再解锁后继组.
  - 本次编排全部完成后, 按「集成与收尾」的统一门禁汇总并询问是否遣散执行 Agent.

### 任务组中的角色与分工

- 主控 Agent 负责:

  - 校验依赖
  - 创建与清理组分支、组 worktree
  - 将执行 Agent 的任务分支交付 ff 到组分支, 核对后放行依赖
  - 订阅通知
  - 安排审核
  - 汇总审核结果
  - finding 派回
  - 组集成
  - 收尾

- 主控 Agent 不做:

  - 不实现子任务
  - 不改子任务代码、worktree、commit; 「主控代做收尾」仅允许清理与记录
  - 不监控其他 Agent 输出

- 组内卡的执行 Agent 负责:

  - 准备本卡工作区, 实现, 验证, 按关注点提交, 按「任务分支交付到组分支」rebase、重验并更新任务分支.
  - 写好 `IMPLEMENTATION` 和`SUMMARY`中的交付, 验收, 验证部分, 填 `TASK_BRANCH` 和最终交付 SHA.
  - 执行 `kander move <task-id> review` 后结束本轮响应, 保留交互式 Agent CLI 会话, 不主动退出进程或关闭终端容器. 任务文件中“退出”也按此解释; 非交互式调用自然结束时, 后续恢复交给 `notify`.
  - 等待 `notify`:
    - 如果收到通知收尾, 就完成本卡收尾, 汇报后结束本轮响应并保留交互式 CLI 会话.
    - 否则按照通知指示执行.

- 组内卡的执行 Agent 不做:

  - 触发审核
  - 更新组分支或将组分支合回 `develop`
  - 收到收尾通知前清理本卡 worktree 与任务分支

### 启动与订阅

- 主控启动前读取全组卡片:
  - 核对 ID, 依赖, 契约和修改范围, 解析每张卡的全部 `PREREQUISITES`, 并把直接引用分为组内卡、组外卡和组外任务组.
  - 运行 `kander check <全部成员 task-id>...` 定向检查引用和依赖环. 缺失卡片、缺失组引用、依赖环或无法隔离的资源冲突阻止受影响卡启动, 保留现场并报告.
  - 不影响启动条件的既有环境问题只记录, 不要求先修复. Agent、launcher、配置依赖、看板或必要 Git 工作区不可用时仍须阻塞, 不绕过 `start` 的前置检查.
  - 使用 `kander move <task-id> todo` 将已确认的 `backlog` 卡片移入 `todo/`, 已处于后续状态的卡片保持原状.

**等待外部依赖**

- 未满足组外依赖时不建组分支、不启动卡, 尚未开工的全组保持 `todo/`.
- 恢复中的后续状态卡保留原状.
- 首次告知缺口与依赖目标, 随后用 `kander subscribe <task-group> <全部成员 task-id>... --watch <组外 task-id|task-group-id>...` 等待, `--watch` 可按直接引用重复传入.
- 组外卡到 `done/` 或组引用全部成员到 `done/` 后复核交付确在 `develop` 可用.
- 观测卡进 `archived/` 或 `trash/` 即停等并交用户决策, 不自判依赖满足.
- 状态事件定向复核外部依赖. 无本组 `working/` 成员时, 15 分钟 heartbeat 仅确认订阅存活; 恢复编排中仍有本组 `working/` 成员时, 按「处理状态变化」检查这些成员的 `liveness`, 不接管组外 Agent.
- 外部依赖全部满足后停止本组的等待订阅, 按「创建与复用」从当时最新 `develop` 建组现场并记录创建锚点, 再启动. 同一主控还负责前置组时继续推进前置组, 不因后继组的等待订阅停止其调度.
- 无外部阻塞时在首卡启动前直接执行.

**启动就绪卡**

- 每张就绪的 `todo` 卡都用 `kander start <task-id>` 启动, Agent 按卡片规模取配置, launcher 默认取 Kander 配置, `--launcher` 只覆盖本次.
- 一个任务组内只用同一种 launcher, 所选 launcher 在当前平台不可用时报告阻塞.
- 首轮启动无组内 `PREREQUISITES` 的卡 (其组外前置已按上述流程全部满足), 之后只启动全部组内前置卡都在 `review/` 或 `done/` 且最新交付已进入当前组分支的卡.
- 同时就绪且无资源冲突的卡并行启动, 禁越过依赖提前启动.
- `start` 的任务文件由命令写入任务 ID 和固定要求, 主控不追加卡片正文或另造任务上下文.
- 执行 Agent 从卡片 `TASK_GROUP` 字段和本规则得知自己走任务组流程.
- 首张卡启动成功后立即告知用户: 本会话是任务组主控, 须保留到本次编排全部任务组按依赖顺序执行完毕, 不要结束当前 session; 提前结束会失去依赖校验, 顺序启动, 适用组级审核和集成. 主控会话持续到本次编排成功或用户明确终止.

- 启动首批后, 主控阻塞读取 `kander subscribe <task-group> <task-id>...` 的逐行 JSON: 先 `snapshot`, 后按状态变化发 `state-change`, 含组 ID、变化前后状态和全组快照.

  用初始快照补齐订阅前迁移, 不依赖历史事件.

**处理状态变化**

- 把带版本的订阅事实当作观测来消费. `task-update` 要求重新读取受影响的交付记录, 即使其状态未变; 修订号不是派发完成回执. 重启时用新快照对照已保存的任务修订号和成员集版本, 而不是进程本地的序号.
- `membership-change` 要求重新核对完整的依赖集. 被移除或改组的成员绝不自动满足其原有义务. `reconciliation_required` 为 true 时, 先对账契约与交付, 再放行依赖.
- 终态的 `membership-unknown` 或 `read-error`, 或 `membership_complete: false`, 停止受影响订阅的依赖放行. 把最后的事实保留为历史, 报告诊断信息, 并遵循明确的恢复要求; 不从被省略的任务推断完成, 也不自动修复看板.

- 收到 `state-change` 后, 主控只对变化卡以及可能因它进入 `review`/`done` 而解除依赖的直接后继卡运行 `kander check <task-id>...`, 读取这些卡片并核对依赖. 初始快照中的 `review/` 卡执行相同交付核对, 不因错过历史事件跳过步骤.
- 进入 `review/` 的卡先按「任务分支交付到组分支」接收; 成功后再判断后继卡是否就绪. 审核关闭时仍须完成此交付核对.
- 新就绪卡仍按既定顺序用 `kander start` 启动.
- 交付已接收的 `review/` 卡在审核适用时进入待审核集合, 否则等待组集成门禁满足.
- 绑定的收尾只有在同一派发 ID/epoch 具有绑定最终交付与集成证据的完成回执, 且卡片处于 `done/` 或已在 `archived/` 且 `RESULT: completed` 时才闭环. 快速往返或重启后快照可以证明这一点; 仅凭所在列不能.
- 新成员启动或经 `notify` 派回后重启订阅, 参数包含当前仍需监控的明确成员集合, 并以新的初始快照继续判断.

- 订阅默认每 15 分钟输出一次 `heartbeat`, 与状态变化无关. 每次 heartbeat 入队后间隔重新计时. 慢探测不阻塞扫描或 heartbeat 的产生; 输出背压超出有界队列/写入期限时明确终止. 此类退出后重新连接并对账新快照.

  主控直接读取事件自带的 `liveness`, 核对修订号/身份、观测时效、有效性和采集状态. 待决、未采集和过期的观测仍为 `unknown`; `alive` 只证明存在, 不延长确认期限也不证明进展, `stopped` 或 `drifted` 按「异常恢复」处置, `unknown` 结合详情报告无法判定.

  不运行全看板 `kander check`, 不重新读取无关卡或自行 capture-pane 巡检.

  Agent 消息或用户输入可触发同范围的额外存活检查, 不改变下一次心跳语义.

- 状态事件之间持续阻塞读取订阅输出, 禁止自行增加短周期轮询. 只有状态事件, heartbeat 或订阅进程明确失败/退出才触发处置; 无输出和等待时间长本身不构成异常.

### 主控持久化恢复

- 记录组进度前, 先用 `kander coordinator claim <claim.json>` 领取, 给出明确的完整成员集、唯一的会话 token、owner 和授权依据. 初始期望修订号/epoch 为零. 恢复时读取 `coordinator show <group-id>`, 并只在既有协调授权下用新 token 以 CAS 方式领取其当前修订号/epoch. 绝不反复重新领取以覆盖另一个存活的写入者. 该 token 只对 checkpoint 写入做围栏; 不授予任何任务接管、集成、传输或清理权限.
- 读取已提交的 checkpoint、当前任务修订号和原始派发, 再调用 `kander coordinator reconcile <observations.json>`. 提供同一完整成员集及每个期望的派发 ID/epoch/base; 已完成的轮次还须写明精确的回执交付 SHA. 初始快照、任务更新、状态变化、heartbeat/attention 事件和订阅者重启都走此路径. 事件只唤醒消费者; 其进程本地序号和状态字符串不是完成证据.
- checkpoint 保存已观测的任务修订号、执行周期、成员集版本、交付、批次/run 引用以及待处理的确认/交付/收尾工作. 它不是第二份任务状态, 也不是审核原件. 同一请求的重试重新校验证据并保留已提交的修订号; 过期的 epoch、修订号、错误的轮次、未知成员或损坏的原件会停止受影响的对账.
- 完整领取中包含等待中的成员. launcher 元数据在其持久化的成功结果存在之前只代表一次启动尝试; 对账让该成员保持等待, 不仅凭该尝试授予任何交付. 消费受控的回滚证据以恢复等待并跟进重试, 包括错过回滚快照的情况. 跨主控重启保留尝试身份、任务/checkpoint CAS 和不可变历史. 成功确认保留执行 Agent 较新的工作; 已确认的周期不能被默默替换. 尝试/结果证据缺失或损坏时停止恢复, 未知的 launcher 结果不得提升为成功. 旧卡和明确的手工领取保留其既有元数据检查.
- 没有派发回执的首次交付要求有已记录的任务分支、`review/`、明确的交付 SHA 及其在所提供绝对 `cwd` 中的实际分支 HEAD. 这只记录一次交付; 组接收和依赖放行仍需各自独立的 Git 核对和既有授权. 绝不为旧卡编造派发回执.
- EOF/输出失败时从当前事实对账一次, 已提交事实有效时重新打开订阅一次. 只有已诊断的受管待决事务才可进入既有的显式 `init` 维护恢复, 重读前至多一次; 仍持续时报告并保留证据. 不重试重复条目、重解析点、损坏记录或未知产物. 锁争用/期限耗尽是观测不可用, 不是执行已停止; 报告并保留游标. 无输出本身不是失败, 不启动任何恢复.
- 把订阅 heartbeat、派发确认期限和任务进展分开. 回执被接受即结束确认等待; 它不证明交付. 其他事件不续期派发期限. heartbeat 或 attention 事件到达时对照已保存的任务/派发修订号; 存活但无变化的成员可能需要进度汇报, 绝不自动换新执行 Agent 或伪造完成.
- 收尾恢复期间, 对账同一派发并消费其绑定的集成产物、全部必需角色结论、不可变的作者处置、已封存的计划和精确的已关闭批次链. 在记录的仓库中重新核对实际 Git 祖先关系和机械证据, 或在清理已移除旧 worktree 时提供仍存在的 worktree 的绝对 `cwd`. 证据中的 commit 身份保持不变. 无 finding 的成员无需仅为复制报告而被通知.
- 部分已归档的已完成成员保留其原始引用和完成回执. 只继续未完成的工作; 不重新集成, 不重复已完成的清理. checkpoint 不授予代做收尾: 只在既有例外下消费专用的带围栏 `dispatch authorize-wrap-up` 授权. SESSION 缺失、交付不确定、非零状态、过期和 alive 观测仍然不足. 成员集或执行周期变化时须对管辖契约做明确对账; 绝不默默丢弃成员或重置 epoch 以绕过证据.

### 审核批次与派回

- 每次角色调用用重复的 `--task` 参数绑定到本批全部成员. 同一批次的各修复轮次保持同一个批次 ID, 每个角色/每次调用使用不同的 run ID, 增量复审给出明确的前序 run ID. 固定要求、CAS 目标推进和同一 run 的发布恢复遵循最小工具协议.
- 把角色报告视为可用之前, 确认其全部卡片发布均已完成. 仅执行成功不等于语义上的 PASS; 失败或中断的证据以及未完成的发布不能关闭批次.

本节仅在审核适用时执行. 仅为任务分支同步或集成冲突派回时按「组集成分支」处理, 不因此启用审核模块.

- 主控按模块、里程碑或依赖链将 `review/` 卡分批, 按「任务分支交付到组分支」接收本批交付后再审核, 不强制整组或逐卡一批.

  按 `KANDER-REVIEW-RULES.md`「任务组的组级审核」确定 CWD、base、task context 和角色流转.

  每批独立, 后批 base 为上批完成审核的 commit, 仅批内修复增量复审.

- 默认分批: 分批时, 已接收到组分支的每张卡都进入同一批. 只有依赖链迫使后卡等待前卡的审核结果时才每卡一批. 禁止对相互独立的卡逐卡串行分批.

- finding 由主控按卡片的修改范围归属: 命中哪张卡的 `GOAL`/`OUT_OF_SCOPE`/实际改动就派给哪张卡.

  跨卡的集成类 finding 派给修改范围命中的卡, 都命不中时主控建一张小修复卡加入本组 (填 `TASK_GROUP` 与 `PREREQUISITES`, `pick` 后 `start`).

**持久化派发身份**

- finding 用 `notify --kind fix --evidence-file <JSON>`, 任务分支同步用 `--kind sync`, 集成后用 `--kind wrap-up --evidence-file <JSON>`. 按命令协议, fix 绑定实际的审核 run/finding/归属和既有作者原件, wrap-up 绑定已核实的 develop 集成. 记录打印出的派发 ID、冻结基线和原始消息; 重试复用同一 ID 和载荷.
- 读取 `kander dispatch show <task-id> <dispatch-id>` 对账不确定状态. 状态变化和终端回显不能代替已接受/已完成回执. 开工前, 执行 owner 使用生成的提示词中带 ID/epoch 的 move 命令; 重放的回执不授权重复工作. 完成时携带同一授权及最终交付/证据引用.
- notify 返回非零时保留实际派发状态. 不编造新轮次, 也不另行调用 resume 以摆脱不确定性. 报告原因; 同一 ID 的重试遵循命令协议持久化的期限、就绪和 stopped/unknown 规则.
- 下文旧有的「只调用一次」notify 表述指一个逻辑派发 ID. 它们不禁止同一 ID 的对账, 也不承诺外部副作用恰好一次. 列的迁移仍只是调度提示; 把绑定的轮次视为已接受或已完成之前先核对派发回执.

**派回 finding**

- 派回只调用一次 `kander notify <task-id> --message-file <findings>` 并检查退出码, 通道选择、恢复与窗口/文档回滚由命令内部完成. 派回只携带门禁 finding (`blocking`, `high`, `medium`, 含 `[mechanical]`); `low`、`recommend` 和 `suggest` 项进入该卡的未处理项清单, 从不派回, 也没有任何派发会要求作者"筛选"非阻塞清单.
- 非零退出即停下报用户.
- 文件写明 reviewer 角色, 档位, finding 原文和主控已知的事实, 不写主控自己的结论. 文件用目标卡的 `LANGUAGE` 书写.
- 原执行 Agent 收到通知后先自行执行 `kander move <task-id> working` 迁回 `working/`, 再带上下文继续: 逐条核实, 修复, 提交, rebase 到组分支头并重验, 更新任务分支, 在 `IMPLEMENTATION` 写上轮 finding 清单、处理结论和最新交付 SHA, 再 `move review` 并结束本轮响应.
- 派发在其不可变的已接受或已完成回执按期望的 ID、epoch 和 base 核实之前一直处于待确认. 初始快照和之后的每个事件都走同一条对账路径. 未观察到 `review -> working` 迁移不妨碍已证明的回执; 观察到迁移或终端回显也不能证明它. 回执存在之前, 不放行依赖、不把其修复交付排入待审核、不创建另一个逻辑派发. 遵守原确认期限, 检查 attention/liveness 事实, 不从超时推断退出.
- 对账同一轮的完成回执和最终交付后, 按「任务分支交付到组分支」接收并同步修复交付, 再消费作者原件并触发适用的增量复审. 已包含的交付只核对和同步; 重复、丢失或乱序的事件绝不产生新的修复轮次.
- 执行 Agent 判为不成立或超出契约的 finding 连同依据回到主控; 主控不得改写, 按 `KANDER-REVIEW-RULES.md`「主代理的核实义务」纳入未处理项交用户复核.
- 一张卡经 `notify` 派回后未进入 `review/` 而执行 Agent 已退出, 或同一 finding 两轮未闭环, 按 `KANDER-REVIEW-RULES.md`「结论与故障处置」的轮次上限处理: 按「异常恢复」记录现状并以编号选项向用户报告, 不改派, 不由主控代修.

### 集成与收尾

- 本组满足「合回与清理前置」后, 主控按 Git 分册「直接集成与 PR」完成已获授权的集成及本地同步; 审核关闭时记 N/A.

  本组任一卡仍在 `working/` 或交付未接收时不合回 `develop`; 不阻止主控按「组集成分支」接收其他就绪卡的交付.

- 集成失败 (rebase, 验证, push 或 ff 未完成), 用户要求暂停或不合回时: 组内卡全部留在 `review/`, 保留组分支, 任务分支与 worktree, 主控记录阻塞及解除条件并按已启用的 `KANDER-REPORTING-RULES.md` 模板 (关闭时如实汇报)逐卡汇报, 末行状态写 `review (阻塞)`.

  只有确实派回事项 (任务分支同步、rebase 冲突、审核 finding、集成成功后的收尾) 时才用 `notify` 派回, 由原执行 Agent 自行迁回 `working/`; 主控不得为表示阻塞而手工迁移卡片.

- 集成成功按依赖顺序派原 Agent 收尾, 无冲突可并行.

  只用 `kander notify <task-id> --message-file <收尾通知>`.

  文件写组分支已集成到 `develop` 的方式及完整 SHA、本卡最终 commit (rebase 改写时含前后对应)、角色结论或 N/A、适用批次与修复轮次、本卡未处理项和「执行 Agent 收尾」清单. PR 集成还须给出 PR 标识、merged 状态与目标分支证据.

  主控不改卡片正文、不手工迁卡.

  无法派回按代做例外.

**执行 Agent 收尾**

- 收到收尾通知的执行 Agent 先自行执行 `kander move <task-id> working` 迁回 `working/`, 再收尾.
- 执行 Agent 按 `KANDER-GIT-RULES.md`「集成与清理」确认本卡改动在 `develop`: 直接集成以最终组 HEAD 核对 `git merge-base --is-ancestor`, 结合通知确认本卡改动包含在内.
- 不用 rebase 前旧 SHA 判祖先, PR 按 Git 分册「集成与清理」的 merged 判据确认.
- 未满足则保留现场并报主控.
- 满足后删本卡 worktree、本地任务分支及适用的远端任务分支, 不删组 worktree 或组分支, 补全总结的审核与收尾 (角色结论或 N/A、适用轮次、最终 commit、组分支与 `develop` 集成结果), 通过受控更新入口发布记录, 再运行 `kander move <task-id> done --result completed`, 按适用 `KANDER-REPORTING-RULES.md` 模板或用户格式汇报并结束本轮响应, 保留交互式 Agent CLI 会话等待用户决定是否遣散.
- 主控不改其迁入 `review/` 前已写的交付、验收、验证记录.

**主控代做收尾**

- 下述例外受持久化收尾授权门禁约束. 先对账同一派发; 不存在时创建绑定的收尾意图. 只有在确认执行 Agent 已退出, 或已授权的重新领取之后出现有效的 stopped 观测时, 才应用 `kander dispatch authorize-wrap-up <request.json>`. 仅凭 SESSION/WINDOW 缺失、notify 结果非零、超时或租约过期不授予权限. 无法确定退出时保留卡片并报告.
- 保留原 OWNER 和作者结论. 在专用授权中记录实际代做者/原因, 接受其新 epoch, 并只使用其清理/只追加记录的范围. 不把仅限收尾的 token 发给另一个执行 Agent, 也不把它升级为普通代码权限. 用同一派发和已核实的集成来源完成; 原有的完成与审核门禁继续有效.


- 无法派回或收尾未闭环时, 主控完成该卡的整套收尾并作为结束者汇报. 适用条件:
  - 卡片没有可用的 `WINDOW`/`SESSION` 记录.
  - `notify` 非零退出.
  - 派回后执行 Agent 已退出, 卡片仍未进 `done/`.

  在该卡完成报告的 `收尾` 和组级汇总里写明「收尾由主控代做」及原因.

- 这是「审核批次与派回」中「不由主控代修」的明确例外, 只适用于收尾: 收尾不改代码, 只做清理和记录.
- 需要改代码的 finding 仍不得由主控代修.

**清理失败**

- 清理中途失败 (某张卡的分支, worktree 删除失败) 时: 已完成收尾并进入 `done/` 的卡保持 `done/`, 不回退.
- 失败卡停在它当时的实际状态 (已派发收尾的在 `working/`, 未派发的在 `review/`), 只保留尚存的 worktree 与分支, 组分支保留.
- 逐卡按真实状态汇报, 失败卡写明失败步骤, 错误和解除条件, 状态写 `working (阻塞)` 或 `review (阻塞)`.
- 代码已在 `develop`, 因此不重新集成, 解除后只继续未完成的收尾.

- 每组全部成员进入 `done/` 后停止该组订阅, 删除该组 worktree、本地组分支及适用的远端组分支, 继续调度本次编排尚未完成的组. 本次编排全部组完成收尾后, 运行一次不带目标的 `kander check`.

  完整检查通过才算成功.

  任一卡进入 `archived/` 或 `trash/` 时, 须等待用户修改组契约或终止整组.

- 编排结束时汇总执行顺序、并行情况、适用审核批次与轮次或 N/A、集成结果, 再逐卡列出已知缺陷、验证缺口和后续任务. 仅在审核适用时另按 `KANDER-REVIEW-RULES.md`「结论与故障处置」分类记录审核未处理项, 不因此加载关闭的审核模块.

  没有未处理项时写"无", 每项另写任务 ID.

  终止时按已启用的 `KANDER-REPORTING-RULES.md` 模板 (关闭时如实汇报)逐卡补发未完成卡的汇报, 再列终止决策.

- 只有本次编排全部组内卡已进入 `done/`, 所有组 worktree 和组分支已删除, `kander check` 已通过且全部组级汇总已完成时, 主控才一次性询问用户是否退出负责这些任务卡的执行 Agent 并关闭对应 herdr tab 或 tmux window. 使用编号选项, 如 `1. 遣散执行 Agent 并关闭对应容器`, `2. 保留会话和容器`; 明确表达相同意图的文字回复也有效.

  未得到明确确认时不执行任何退出或关闭动作.

  用户拒绝时保留全部会话和终端容器, 主控结束本次编排.

- 用户确认后, 主控对每张组内任务卡只调用一次 `kander dismiss <task-id>`, 不直接向 Agent 发送退出指令, 不直接关闭 tab/window, 也不绕过命令的身份、拓扑和优雅退出门禁.

  各卡的遣散结果相互独立: 某卡返回非零时保留其现场并记录原因, 继续处理其余组内卡.

  全部尝试结束后汇总逐卡结果.

  这是任务组完成后的可选终端清理, 失败不回退已完成卡片, 不恢复已删除的分支或 worktree, 也不改变已发出的完成报告和组级结论.

## 机械汇总与作者边界

审核适用时, 主控在关闭批次前建立本组的执行审核计划. 通过既有规则确定角色适用性, 记录明确的 N/A 理由和规则依据. 用未封存的计划做渐进分批; 只有在上一个已关闭目标已知后, 才带期望的计划修订号追加每个后续批次, 再在收尾前封存. 保持固定的周期成员集和既有批次证据.

用受控归属命令归属 finding. 共享 finding 写明全部受影响的卡. 把实际 finding 派发给其原执行 owner. 每个 owner 提交自己不可变的处置原件和修订. 主控引用这些记录, 可以用自己的作者身份另行记录自己的核实意见; 绝不改写或冒充执行侧结论.

用 `kander review aggregate <CWD> <batch-id>` 把完整处置机械地发布给全部成员. 无 finding 的成员不会仅为复制报告而被派发. 汇总不是作者核实, 也不代执行 owner 决定验收.

接收批内修复, 对同一批次目标做 CAS, 并执行必需的增量复审. 仅含机械项的修复可用受控推进命令在不新起 reviewer 的情况下推进目标, 沿用既有机械证据规则. 只有通过审核关闭命令, 且全部必需角色、作者处置和最终 Git 关系都已满足, 才关闭批次. 只从该精确的已关闭目标开启下一批. 收尾期间, 除实际 develop 集成外还核实已封存的计划和全部关闭记录; 保留未处理项和全部原始作者记录.

- 用 `move working --owner` 重新领取已纳入计划的卡可能改变其执行周期绑定. 此时 `review progress` 报告 `requirements-needed` 和完整的 `rebind_cycles` 映射. 用 `review extend-plan` 带既有计划 ID、期望修订号、该映射、作者和依据为整个计划恢复相同要求. 该操作不能改变批次、封存、角色要求、成员状态或更早的证据. 旧的失败和 finding 仍然有约束力; 禁止另建计划来丢弃它们. 后继 OWNER 可以对已归属的 finding 追加自己的处置, 保留旧作者不可变的原件和记录谱系. advance 和 extend-plan 使用计划的精确 CWD.
