# 审核规则

仅在 `rules.review=true` 时自动加载并判断触发.

用户明确要求本次完整审核流程时也可读.

优先级与加载流程见 `KANDER-AGENTS.md`.

单次 `kander review` 的参数和只读门禁见 `KANDER-BASE-RULES.md`, 不自动启用完整流程.

- 本模块不依赖 Git 工作流.

  `rules.git=false` 时沿用用户分支与交付流程, 按任务开始记录的 base 或用户明确范围确定审核 base.

  首轮前固定完整 SHA, 不猜 develop 或建分支.

  提交审核对象须按用户授权.

- 本文涉及 rebase、合回和清理的 Kander Git 机制仅在 `rules.git=true` 时读取 `KANDER-GIT-RULES.md`; 关闭时审核完成即回到用户流程.
- 任务组相关条款仅在 `rules.task_groups=true` 时适用, 固定完成报告仅在 `rules.reporting=true` 时适用, 不通过引用加载关闭模块.

## Reviewer 选择

- 支持 Codex, Claude, Grok, Cursor 与 Kimi 五个 reviewer.

  所有平台的公开审核入口都是命令根下的 `kander review`, 进入单一门禁实现.

  Windows 优先使用 Reviewer `.exe`.

  只有 `.cmd`/`.bat` 时通过显式 `cmd.exe /d /s /v:off /c` 和五种 reviewer 适配层的参数编码启动.

  这不是任意批处理脚本的通用调用契约.

  除下表的 CLI 与隔离参数外, 本文件全部规则对五者一致.

  命令入口按 `KANDER-AGENTS.md`「作用域」选择.

| reviewer | agent 参数 | CLI            | 入口的隔离参数                                                                                                                       |
| -------- | ---------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Codex    | `codex`    | `codex`        | `--sandbox read-only`, `--ephemeral`                                                                                                 |
| Claude   | `claude`   | `claude`       | `--permission-mode bypassPermissions`, `--disallowedTools Edit,Write`                                                                |
| Grok     | `grok`     | `grok`         | `--sandbox read-only`, `--no-memory`, `--no-subagents`                                                                               |
| Cursor   | `cursor`   | `cursor-agent` | `--print --output-format json --trust`; `CURSOR_CONFIG_DIR` 与 `CURSOR_DATA_DIR` 指向本轮隔离 runtime; 无 `--sandbox` / `--mode ask` |
| Kimi     | `kimi`     | `kimi`         | `--prompt --output-format stream-json --agent-file <round's definition>`, 其 frontmatter 只放行 `Read, Grep, Glob`; 命令行上不存在隔离标志 |

**Reviewer 隔离**

- Codex 与 Grok 使用沙箱强制的只读隔离: Codex 在目标 worktree 内运行只读 shell. Kimi 通过其本轮定义的工具放行列表实现只读, 见下文.
- Claude 与 Grok 在树外 runtime 运行; Grok 只开放读取、搜索工具, 而 Claude 以完全授权运行, 使用除 `Edit` 与 `Write` 外的全部工具集, 只读靠这一点加上 prompt 保证. 与 Cursor 一样, 事后检查只看目标 worktree 的 Git 可见状态: 该 worktree 之外的写入以及其内被忽略路径的写入都不会被检测.
- Cursor 仅隔离配置与会话到 runtime, 只读靠 prompt 与事后工作树校验, 不事前阻断, 不检测树外写入.
- 所有平台完整 prompt 写 UTF-8 任务文件, Reviewer 仅接收路径短指令.
- Grok 保留 `--prompt-file`. Kimi 没有 prompt 文件也没有 stdin, 同一句简短指令直接内联传给 `--prompt`.
- Kimi 没有沙箱、权限或工具标志, 且 `--plan` 不能与 `--prompt` 同用. 因此只读来自为本轮写出的 Agent 定义: 其 frontmatter 的工具放行列表就是模型拿到的全部界面, 所以会改动和外联的工具从未暴露, 而不只是被拒绝. `KIMI_CODE_HOME` 保持在 reviewer 的真实 home, 已存凭据无须复制即可继续使用. 因为没有 `--cwd`, 它在目标 worktree 内运行, 并通过 `--add-dir` 读取 prompt、证据和自己的定义.
- 任务文件不检查或收紧 POSIX 权限、Windows ACL, 位于审核 runtime 时仍受其边界保护.
- Reviewer 退出后须强制收尽进程组, 失败即审核失败.
- 当前只有 Cursor 自带不等待收尾的帮手进程, 对其仅将脱离父链的 detached 后代判为残留并拒绝结果, 普通子进程不因此拒绝.
- 其他 Reviewer 退出瞬间进程组非空即拒绝.
- 工作树校验仅看 Git 可见状态, `.gitignore` 排除路径的写入不使审核失败.
- Claude 的树外 spec 先快照到当前用户独占 runtime, 不授权原父目录.
- runtime 沿用最小工具协议的权限、固定句柄和有界 no-follow 清理契约: POSIX `0700`.
- Windows `CREATE_NEW`, 随机名碰撞安全重试, 当前用户独占的受保护 DACL.
- 根句柄持续持有至 worktree 校验和清理结束.
- reparse point、占用、预算耗尽等清理失败均拒绝结果, 禁静默遗留.
- 禁为统一实现或适配 Windows 更换、放宽隔离参数.

- `PM`, `CSA`, `Hacker`, `QA` 各选 reviewer, 按优先级取首个明确来源:
  1. 当前用户指令.
  2. 最近的项目 `AGENTS.md` 或 `CLAUDE.md`.
  3. 用户全局规则.
  4. 当前作用域角色配置.

  前三档未指定时由命令根的 `kander review` 读取第 (4) 档, 配置不存在则 Codex.

  判定所需规则文件未加载时读取, 不可读视为未指定.

- 不同角色可以使用不同 reviewer. 同一角色的修复重跑和结论确认必须继续使用该角色在当前批次选定的 reviewer: 增量链要求同一 reviewer, 且关闭会拒绝该角色任何未与选定结论相连的成功执行的运行. 因此用户指定的更换只有在该角色在同一批次内尚无成功执行的运行时才可行 (其失败的运行通过 `resolved_failures` 绑定); 已有成功运行的角色在本批次由同一 reviewer 完成, 更换从下一批次起生效.
- 下文的「reviewer」和「reviewer CLI」均指当前审核角色选定的那一个; 「审核入口」指命令根下的 `kander review`. 「主代理」指核实 finding 并就其与用户沟通的 Agent: 单卡为执行 Agent; 任务组中, 批次安排, 汇总与用户决策由主控承担, 核实与处置自己被归属的 finding 由各执行 Agent 承担 (见「主控与执行 Agent 的核实分工」). 「交付说明」指卡片的 `SUMMARY` 段 (大卡为 `report.md`), 非看板任务则指给用户的最终交付消息.

## 目标与边界

- 审核目标: 计划或用户目标完整、正确落实, 流程闭环, 无直接相关的逻辑漏洞或回归; 禁扩大任务范围.
- `QA` 先查项目架构、模块职责、依赖方向、公开边界和集成模式, 再查直接相关的正确性、回归、可测试性与代码质量 (单一职责、可读性、改动局部性、耦合与重复、错误和资源处理).

  `QA` 不做通用性能审核或报告性能 finding.

  明确性能验收由 `PM` 按契约核对.

- `QA` 限制非生成代码文件为 1000 个物理行, 仅在本轮新增文件超过 1000 行、被触及文件在 base 不超过 1000 行而现在超过 1000 行、或被触及的既有超限文件净增行数时报告 gate finding; 最后一种情况在改动只替换 import、适配或胶水代码时豁免. 这些条件与 `KANDER-CODE-RULES.md`「交付自检」第 2 条相同.

  不清查无关超限文件, 最终行数不高于 base 时也不触发.

- `QA` finding 限 task context、既有契约或本轮涉及代码及模块边界中的现实可达问题. 禁穷举拼凑条件、极端边界、臆造故障或低现实性问题; 任务相关现实风险覆盖后停止, 不扩为仓库质量巡检.
- 只处理本任务引入、加剧或掩盖的问题. 既有且未加剧或掩盖的问题不要求修复、不阻塞审核或集成、不交用户决策; 用户明确纳入本轮除外.
- 审核结果若要求改变超出用户明确目标的业务逻辑, 用户流程或对外契约, 必须向用户说明影响并由用户决策; 禁仅据审核结论自行选择或实施该变更.
- 凡需用户注意或决策的问题, 主代理逐项详解问题内容, 触发条件, 实际影响和建议处理方式, 标明提出该问题的审核角色, 再给编号选项; 禁只给抽象选项, 汇总多 Agent 结果时不得丢失来源归属.
- 运行环境问题若影响验证可信度, 交付可用性或用户数据安全, 必须明确告知用户.

  除非改动直接引入, 加剧或掩盖该问题, 或用户明确要求处理, 否则只记为验证事实, 禁单独判为 blocking, high 或 medium, 亦禁据此要求无关修复.

## 前置条件与执行

- 审核触发采用白名单: 任务命中下列任一条目才进入审核, 未命中一律不自动审核. 用户明确要求审核时无条件进入, 不受白名单限制.
  1. 明确的功能开发或 Bug 修复任务.
  2. 超出小改动阈值的代码修改: 相对审核 base 改动的代码文件超过 1 个, 或新增与删除行合计超过 10 行. 以 `git diff --numstat <base>..<commit>` 为准, 只统计代码文件, 不计 `*.md` 与 `*.markdown`; 二进制文件一律豁免.
  3. 安全敏感改动, 不论大小: 认证授权, 凭据, 加密, 权限校验, 沙箱与隔离参数, 或其他直接影响安全边界的逻辑.
  4. 对外契约变更: CLI 参数, 配置 schema, 持久化数据格式, 网络或插件 API 的新增, 修改或删除.
  5. 不可逆或跨数据操作: 数据迁移脚本, 批量改写或删除用户数据, 及其他无法用简单回滚恢复的操作.
  6. 构建, 安装, 发布, CI 或审核门禁流程本身的改动.
  7. 依赖变更: 新增, 升级或移除外部依赖.
  8. 测试的删除或放宽: 删除测试, 跳过测试, 放松断言或降低覆盖.
  9. 删除或重命名公共模块, 或跨模块重构.
- 白名单按任务实际改动和用户表述判定, 不靠任务标题或标签; 禁把命中条目的任务改述成未命中类型以绕过审核.
- 未命中白名单跳过审核时, 必须在集成前明确告知用户"本次未触发审核白名单, 未走审核闭环", 并写明改动范围 (改了哪些文件, 新增与删除行数). 禁静默跳过. 用户随后要求审核时照常执行完整流程.

**审核工具不可用**

- 选定 reviewer 的 CLI 或当前平台审核入口在本机不可用时无法审核: 明确告知用户"本机未装 <reviewer> CLI, 无法执行审核", 保留分支和 worktree, 并给编号选项 `1. 装好该 CLI 后重试`, `2. 改用另一个 reviewer 重启审核`, `3. 跳过本次审核直接集成 (风险由用户承担, 在交付说明记录未审核)`, `4. 停止集成`. 选项 3 仅在该角色的要求尚未在批次中冻结时存在, 即批次首次运行之前; 一旦批次把该角色记为 `required`, 关闭就需要其成功运行, 只能在 1, 2, 4 之间选择.
- 审核入口缺失时还须说明需重新安装 Kander.
- 禁自行跳过, 禁未经用户明确指定就换 reviewer.

- 审核前, 把审核 base 以来全部任务改动按关注点提交, 保持 worktree 无未提交或未跟踪文件.
- 审核前, `rules.code=true` 时作者完成 `KANDER-CODE-RULES.md`「交付自检」并记录; 代码模块关闭时, 作者至少核实 `git diff --check`, 下文「固定归档」的三类问题, 以及定向测试已在最终 commit 上运行, 并记录. 自检本应发现的 finding 仍是普通 finding: 其中机械项作为 `[mechanical]` 项按「固定归档」闭环, 其余走正常修复轮次. 自检失败记在卡片上; 它绝不是额外的一轮审核, 也绝不是审核流程之外的退回.

**审核 base**

- Git 模块启用时: 专用任务分支 base 为最近基于 `develop` 创建或 rebase 所用的 `develop` 完整 SHA.
- 同一 base 下修复不换 base.
- 审核开始即冻结, 闭环结束前不追 `develop` rebase, 不更新 base.
- `develop` 前进留到集成处理.
- 集成 rebase 后 base 更新为新基点, 是否重审按 `KANDER-GIT-RULES.md`「集成与清理」的一次性门.

标准审核分两个阶段.

各角色是否运行先按「审核环节」解析, 跳过的标 N/A.

`PM` 与 `QA` 在第一阶段基于同一 commit 并行首轮, 安全角色在两者都通过后进入第二阶段.

审核重点仍按「审核档案」确定.

阶段流转以本图为准, 每次修复只对提出该必修项的角色做增量复审:

```text
[1] PM || QA    基于同一 commit 并行首轮. PM 核对实现是否完整达到 task context;
                QA 核对功能正确性, 回归, 测试与代码质量; 免跑或跳过的角色标 N/A 并直接通过
     |  任一角色有必修 finding --> 合并两个角色的必修项一次修复并提交 (同一 base, 新 HEAD)
     |                          --> 只对有必修项的角色增量复审 (两者都有则并行) --> 回 [1] 直到两者都通过
     |  某角色仅剩机械必修项 --> 修复并提交, 主代理机械核实 --> 该角色在新 HEAD 通过, 不重跑
     |  已通过的角色不因另一角色的修复重跑 (见「结论沿用」)
     v  PM 与 QA 均通过
[2] CSA/Hacker  按环节策略与触发条件决定; required 可越过触发条件; 两者均触发可并行; 均未运行标 N/A 并直接通过
     |  合格 finding --> 用户决策 --> 1 修复并提交 --> 增量复审 [2]; 修复范围由 QA 增量复审, 改变功能行为时 PM 也增量复审
     |                                  QA/PM 的后续修复实质改动安全相关代码 --> 对应安全角色增量复审 [2], 直到各方都通过
     |                           --> 2 确认通过 (交付说明记录接受的风险与理由)
     |                           --> 3 停止集成 (保留分支与 worktree)
     |                           --> 看板任务 15 分钟无决策: 超时忽略 --> 阶段结束
     v  阶段结束
   审核完成 --> 向用户展示全部未处理项 --> 进集成流程
```

增量复审: 同一角色在同一 base 下的第二轮及之后一律是增量复审, 不再全量重审.

- 增量复审以该角色上轮审核的 commit 为 `reviewed-commit`, 须严格位于 base 与新 HEAD 之间. 任务绑定的调用从 `--previous-run-id` 推导该值; 显式传入的值必须与之一致. 未绑定的调用按位置参数传入.

  仅 `reviewed-commit..commit` 为新材料.

  reviewer 逐条核实上轮 finding 闭环, 只报告修复引入、加剧、掩盖的问题或对触及需求的破坏.

  未变代码视为已接受, 禁重新审计或扩大范围.

- review context 必须包含上轮每条 finding 及主代理的处理结论. 任务绑定的运行由工具自动纳入原始报告, 作者记录和批次视图; 按位置参数传入的 review-context 作为单独分隔的补充保留. 未绑定的运行由调用方提供完整上下文: 成立项写修复 commit 与验证结果, 不成立项写核实依据, 无法核实项写用户决策.

  reviewer 只核对这些事实, 主代理不得省略或改写上轮清单.

- 首轮不传 `reviewed-commit`. 该角色 PASS 后不再重跑 (见「结论沿用」). base 变更或 task context 变更意味着新批次, 该角色在其中从全量首轮重启; 更换 reviewer 仅按「Reviewer 选择」才可行.
- 主代理的核实义务不因增量复审减少: 增量复审的每条结论同样逐条核实.
- 某角色已在本 base 上出过报告, 其修复轮次若不以增量模式运行 (任务绑定的 `--previous-run-id`, 或位置参数 `reviewed-commit` 加完整上轮清单) 即为无效. 不要在同一批次为该角色再启动一次全量首轮: 工具不拒绝启动, 但关闭会拒绝未与选定结论链相连的成功执行的运行, 批次将因此无法再关闭. 之后仅有的全量首轮是失败运行的重试 (通过 `resolved_failures` 绑定) 和新批次的首轮.

- 分级: 全部角色的输出按下表六档标注. 新 schema 报告中缺档的项目输出校验失败 (见「受控计划, 作者处置与批次关闭」); 仅对旧的非结构化报告, 主代理才在 `map-legacy` 映射内补判缺失的档位.

| 档位       | 含义                                                   | 是否必修 |
| ---------- | ------------------------------------------------------ | -------- |
| `blocking` | 目标未达成, 或改动导致数据损坏, 安全失效, 主流程不可用 | 是       |
| `high`     | 常见路径上必然出错或回归, 触发条件明确                 | 是       |
| `medium`   | 特定条件下出错, 或契约, 边界, 错误处理有真实缺陷       | 是       |
| `low`      | 确实是缺陷, 但触发罕见且后果可忽略                     | 否       |
| `recommend` | 不是缺陷, 但按项目规则或既有约定应当改的做法           | 否       |
| `suggest`   | 可选改进, 取舍由负责人决定                             | 否       |

- 固定归档: 下列问题不因触发罕见或后果轻微降档, 一律至少判 `medium`, 任何角色发现都适用:
  - 文档或代码注释与实际实现不一致.
  - 死代码 (不可达, 或无任何调用与引用的代码).
  - 多余的测试 (重复覆盖同一行为, 或断言与被测行为无关的测试).
- 机械必修项为上文「固定归档」所列的三类问题, 报告标 `[mechanical]`. 它们与门禁 finding 一起派发, 修复并提交, 由主代理的机械证据 (注释逐句对照、引用搜索输出或测试清单) 闭环.

  某轮成立的必修项全为机械项时一律不重跑 reviewer; 该角色经机械核实后即在新 HEAD 通过.

  混有非机械项时, 增量复审只覆盖非机械项, 并说明机械项已由调用方闭环; 机械项不单独计轮.

  漏标 `[mechanical]` 由主代理按定义补判, 禁将非机械缺陷归入以省复审.

- 报告档位用英文标识: `blocking`, `high`, `medium`, `low`, `recommend`, `suggest`.

  前三档进报告的 `FINDINGS` 数组, 后三档进其 `NON_BLOCKING` 数组. 新 schema 报告缺任一数组即输出校验失败, 用新 run ID 重试. 只有旧的非结构化报告可以没有非阻塞段; 此时映射记为"该角色未提供非阻塞项", 并将该说明加入未处理项清单.

- 必修门槛: 只有经主代理核实认可的 `blocking`, `high`, `medium` 才必须修复. `low`, `recommend`, `suggest` 一律不阻塞审核和集成, 按「结论与故障处置」记录处理结论.
- `low`, `recommend`, `suggest` 项一律不开启修复轮次. 关闭仍要求被归属作者对其中每一项给出处置 (`fixed`, `deferred` 或 `rejected`, 各附依据), 因此它们随该卡门禁 finding 的同一次 `--kind fix` 派发的消息送达作者, 标注"仅处置"; 修复证据只绑定 `FINDINGS` 项, 绝不绑定 `NON_BLOCKING` 项. 只有非阻塞 finding 的卡片不能收到绑定的 fix 派发: 用标注"仅处置, 不改代码"的 `--kind sync` 派发发送这些项, 作者提交处置后对未变更的交付 `move review` 完成该轮. 它们连同作者的处置记入卡片的未处理项清单, 在下次交付或后续卡中处理. 禁止不按角色与档位列出各项就要求作者"分诊"的派发.
- 第二阶段只把实际运行的 `CSA` 或 `Hacker` 返回且经主代理核实成立的 `blocking`, `high`, `medium` finding 交用户决策.

  每项列出问题, 影响, 修复方法及至少三个选项: `1. 修复并重审`, `2. 确认通过并接受风险`, `3. 停止集成`.

  其余档位和纯 defense-in-depth advisory 直接进未处理项清单, 不触发决策.

- 仅看板任务适用安全 finding 超时.

  每项从完整信息和选项送达用户时独立计时.

  同批共用发送时间, 部分回答不停止其余项.

  15 分钟无明确决策即标记"超时忽略", 记录角色, 档位, 问题, 影响, 发送时间, 超时时间和理由, 再继续.

  "超时忽略"不等于 `PASS`, 用户确认或接受风险.

  卡片完成前收到决策则按最新指令处理.

- 非看板任务及 `PM`, `QA` finding, 无法核实项, 契约或负责人变更, 以及用户明确要求的验收, 集成确认不得超时跳过.

**调用参数**

- 调用: 未指定 reviewer 用当前作用域 `kander review <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context] [reviewed-commit]`, 由配置分发.
- 已指定用 `kander review <reviewer> <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context] [reviewed-commit]`.
- Windows 全局安装的人工普通参数示例: PowerShell `& "$env:USERPROFILE\.local\bin\kander" review ...`.
- 批处理与 Windows PowerShell 5 不能保证任意 argv 无损.
- 含 `&|<>^%!`、引号或边界反斜杠的数据禁由程序调用 `.cmd` 或拼 shell 字符串.
- 自动化须用进程 API 的 argv 数组直启命令根 `kander` (全局为 `Path.home() / ".local/bin/kander"`), `review` 及各参数独立传入.
- 不得绕过 Kander 直调 reviewer CLI.
- `CWD` 为目标 worktree 绝对路径.
- commit 参数均为完整 SHA.
- base 为 commit 祖先, `HEAD` 等于 commit, 无未提交或未跟踪文件.
- 仅增量复审使用 `reviewed-commit`, 须严格位于 base 与 commit 之间. 任务绑定的运行从 `--previous-run-id` 推导该值, 并自动保留完整的上轮报告与作者结论; 显式传入的值必须与之一致. 调用方的 review-context 为可选补充. 未绑定的增量运行须按位置参数传 reviewed-commit, 且 review-context 非空并含完整的上轮 finding 清单与结论.

**结论沿用**

- 结论沿用: 完整审核各角色共用 `CWD`、base、task context.
- 同时触发的 `CSA` 与 `Hacker` 使用同一 commit.
- 同一 base 下已通过角色不因其他角色修复重跑, 除两种交叉复审: 安全修复由 `QA` 复审, 改功能行为时含 `PM`.
- `PM` 或 `QA` 后续修复实质改变安全代码时, 对应安全角色对修复范围复审.
- 各角色通过 commit 可不同, 同一 base 内最终 commit 须为各通过 commit 的后代.
- 用户换 base、重建分支、审核期被迫 rebase 等非集成变更使全部结论失效. 由于每个有 reviewer 运行的批次仍须先关闭, 其卡片才能完成, 先在当前目标上关闭未关闭的批次: 其余必需角色仍在该处运行, 被取代的 finding 以用户决策原文为依据处置为 `rejected`. 同一 base 链上的 task context 变更随后在同一尚未封存计划的新批次中继续; 该批次从上一个已关闭目标开始, 只审其后的工作, 因此已关闭范围不在新契约下重审. 用户要求在新契约下重审已关闭范围, 或 base 或历史已变更时, 按「任务组的组级审核」作为新卡片和新计划下的新工作继续. 无论哪种情况都要报告浪费的轮次.
- 集成中因 `develop` 前进而 rebase 按 `KANDER-GIT-RULES.md` 一次性门沿用结论, 不要求重写前 SHA 仍为祖先.
- task context 为权威需求契约: 短任务用字符串, 长任务用可读绝对 spec 路径.

**报告文件与稳定标识**

- 未绑定任务时, 每个角色的 stdout 单独存为报告, 放在目标 worktree 外仅当前用户可访问的临时目录. 该目录只放报告, 本轮通过, 终止或第二阶段决策完成后清理; 需保留诊断先向用户说明.
- 看板审核时, 在 CWD 之前用重复的 `--task <id>` 参数传入每张被审卡片, 并带 `--batch-id <id>`. 创建意图时和卡片首次发布时都要求 working/review 中的目录卡片和统一的报告语言; 旧的文件卡片须先按 init 维护协议处理.
- 批次在首次运行前按 `KANDER-KANBAN-RULES.md`「审核证据完成门禁」在审核计划中命名 (首批在创建计划时, 之后由 `extend-plan`); 随后首次运行以绝对 JSON 路径提供 `--requirements-file`, 列出全部角色 (`PM`, `QA`, `CSA`, `Hacker`), 取值为 `required` 或 `N/A: <reason>`, 按既有优先级与环节规则解析并与计划条目一致. 要求, 成员, base, task-context 字节和报告语言在批次内固定. 若实时 spec 变更或移动, 后续角色, 修复轮次和恢复重试必须传归档的 `task-context.md` 的绝对路径, 以保留原始字节和批次 ID. 卡片发布前, 原始输入可在运行控制目录的 `inputs/task-context.md` 下取得.
- 每次实际调用 reviewer 用不同的 `--run-id`. 省略时生成随机 ID 并打印到 stderr, 随后记录该 ID. 同一 commit 上的 PM/QA 共用批次 ID, 使用不同的 run ID. 时间戳不确立身份或前驱顺序.
- 输入完全相同的同 ID 重试不再启动 reviewer, 只校验既有证据并补齐缺失的卡片发布. 若原门禁进程在定稿前结束, 恢复时将该运行标记为中断, 保留部分原始输出, 不伪造报告或成功清理.
- 任务绑定的增量调用带 `--previous-run-id`; 前驱必须已在同一批次, base, 角色和 reviewer 下完整发布, reviewed-commit 的规则见「调用参数」. 工具保留其原始报告, 作者记录和批次视图; 调用方上下文只是逐字保留的补充, 绝不替代.
- 修复时保留批次 ID. 要推进其目标, 传绝对路径的 `--advance-file` JSON, 含 `previous_target`, `target`, 非空的 `reason`, 以及把该精确 Git 范围内每个 commit 映射到成员任务 ID 的 `deliveries`. 调用方提供真实的任务归属; 命令校验范围与成员资格并执行 compare-and-swap. 未完成的执行或未完成的发布必须先结清. 不得纳入批外交付.
- 每张卡片在 `reviews/<run_id>/` 下保留完整的不可变原件: 输入上下文, 原始输出, 日志, 任何有效报告, sidecar 和 manifest. 创建意图后的启动失败, 超时, 无效输出, 残留进程和清理失败同样保留证据. 预检失败不伪造已执行的运行. 报告语言由卡片 LANGUAGE 冻结, 仅在缺失时回退到配置.
- 工具在 REVIEWS 中每次运行追加一行 JSON 索引. 不得从 reviewer 的叙述推导该索引, 不得把报告粘贴进正文, 不得通过 update 编辑原件, 不得在临时清理时删除已归档证据.
- 新的结构化报告若 findings 缺失/无效或 lineage 关系无效, 在定稿时输出校验失败: 以 `execution_status=failed`, 非零门禁退出码和确切的校验原因归档, 保留报告与原始输出. 在同一批次内用新 run ID 重试: 失败的首轮按全量调用重试; 失败的增量轮次沿用其上一个有效的 --previous-run-id 与 reviewed-commit, 保留该成功的前驱链. 绝不把失败的运行选为前驱, 也不用不相连的全量轮次替换既有有效链. 不重复失败意图已提交的推进. 通过 `resolved_failures` 显式绑定每次失败尝试; 同 ID 恢复绝不再启动 reviewer.
- `execution_status=ok`, 可读的 stdout 和命令零退出码不意味着语义上的 PASS. 按本审核流程解读实际报告. 失败/中断的运行绝不确立通过的角色.
- 审核待定期间允许普通更新以及在 working 与 review 之间移动. 任何终态移动前先完成发布. 下文的审核计划与处置门禁在执行周期完成前阻止 done. 被外部旧写入方过早移动的卡片在控制目录中保留未发布的原件, 显式的 `kander check <task-id>` 或 `kander check --all` 仍会诊断出发布不完整. 不得把 done 卡片移回, 也不得绕过受控写入去修复它.
- 发布只在进程收集, worktree 校验和运行时清理之后才结清. 每张卡片的发布是原子的; 跨卡失败保留已成功的发布, 报告每张失败卡片并以非零退出. 解决错误后用同一 run ID 重试; 若需要 init, 遵守其维护前置条件. 未完成的发布不得计入批次完成.
- `kander check` 校验意图, manifest, 索引, 原件哈希, 语言, 成员资格和前驱关系. 它不推断语义上的 PASS, 也不关闭批次.
- Reviewer 隔离参数和运行结束时的 worktree 校验仍然适用; 不得绕过门禁.

## 任务组的组级审核

看板任务组 (见 `KANDER-TASK-GROUP-RULES.md`「任务编排」) 不逐卡审核, 由主控 Agent 在组集成分支上分批审核.

单卡任务仍按上文逐卡执行.

本节只改变审核单位与角色分工, 环节策略, 增量复审, 核实义务和结论要求全部沿用.

- 审核单位是批次: 没有批次开启时, 主控按 `KANDER-TASK-GROUP-RULES.md`「组集成分支」把就绪的 `review/` 交付接收到组分支并核对, 待全组每个成员都已启动后, 对自上一个已关闭目标以来接收的全部交付开启一个批次, 按模块、里程碑或依赖链步骤选择时机. 一批的 diff 应能被 reviewer 精读, 批次契约须覆盖从本批 base 到 HEAD 的全部未审核交付; 已接收的交付绝不被排除在其后的批次之外. `review/` 状态不能代替组分支交付核对.

  全组至少一批, 不强制每卡一批.

  白名单按该批实际改动汇总判定.

  任务组含功能开发或 Bug 修复卡时一律进入审核.

- 每个批次是一次独立的完整审核.

  `CWD` 为组分支专用 worktree 的绝对路径, commit 为当前组分支 HEAD.

  首批 base 为组分支创建时所基于的 `develop` 完整 SHA, 后续批次 base 为上一批按「结论与故障处置」的已关闭目标, 因此每批只审自己新引入的改动.

  其余前置条件不变: `HEAD` 等于 commit, worktree 无未提交或未跟踪文件, 全部 commit 参数为完整 SHA.

  批次进行中, 批外新交付排队, 不更新组分支. 批内修复须等 Reviewer 退出后由主控 ff 接收再复审, 不在 Reviewer 运行期间改变审核工作树或 HEAD.

- task context 为该批全部卡片的完整契约合并成的 spec 文件, 放在仅当前用户可访问的临时目录并以绝对路径传入. 逐卡标明任务 ID, 保留「task context 与 review context 模板」的全部六项契约字段, 以及卡片的 `DISCUSSION`, 不省略用户取舍、验收条件或威胁模型.

  不得只传一张卡或只传任务组名.

  卡片的`OUT_OF_SCOPE`仍是 finding 越界判定的边界.

- 批次之间不沿用结论, 不做跨批增量复审: 不同批次的 task context 不同, 按「前置条件与执行」的失效条件 (task context 变更使该角色重启) 必须从全量首轮开始, 首轮不传 `reviewed-commit`.

  批内修复轮次才是增量复审: 同一 base, 同一批次 task context, `reviewed-commit` 为该角色上一轮审过的组分支 commit, review context 含上轮 finding 清单.

  上一批的未处理项写进后续批次 task context 的排除项, 不重复报.

- 跨重定 base 或重新拆分的任务组沿用结论: 用户授权把交付重放到新 base 时, 该重放是新卡片和新计划下的新工作, 因为计划不能串接 base 不是上一个已关闭目标的批次, 且其成员与 worktree 固定; 先前的批次已关闭并作为历史保留. 在该批次的 review context 中, 把内容与先前已关闭目标逐字节相同的文件列为已审核, 让各角色聚焦于冲突解决期间改动的文件和批次上下文点名的集成接缝. 这是 review context 内的指示; 在工具层面该批次仍是不传 `reviewed-commit` 的全量首轮.

**主控与执行 Agent 的核实分工**

- 主控负责触发角色、存报告、通过 `review assign` 按修改范围归属 finding (finding 归属到本批中范围被其命中的每张卡; 批外的卡不能被归属, 归属规则含未命中任何本批成员范围的 finding, 见 `KANDER-TASK-GROUP-RULES.md`「审核批次与派回」), 用 notify 将 finding 原文、角色、档位派回各原执行 Agent.
- 不另调 `kander resume <task-id> --message-file`, 恢复由 notify 内部选择.
- 主控汇总回传清单为 review context、触发增量复审、展示全部未处理项.
- 执行 Agent 承担「主代理的核实义务」: 逐条核实, 成立项在本卡任务分支修复、提交、rebase 最新组分支并重验, 按 Git 分册更新任务分支; 不成立或无法核实项写依据. 执行 Agent 不更新组分支.
- 每条结论通过 `review disposition` 提交, 再在 `IMPLEMENTATION` 写入一条条目, 含各状态的计数、处置记录的卡片相对路径和最新交付完整 SHA (绝不写 finding 清单本身, 按 `KANDER-KANBAN-RULES.md`「契约与记录」), 再 `move review` 并结束本轮响应. 主控先核对并 ff 接收修复交付, 再触发增量复审.
- 主控不得替其判定成立与否, 不得省略或改写结论.

- 安全角色按「审核环节」与触发条件在整批通过第一阶段后运行, `CSA` 与 `Hacker` 基于同一组分支 commit; 用户决策与超时规则不变.
- 有效组级审核须各批次的实际角色满足「结论与故障处置」, 后批 base 等于前批的已关闭目标, 连成覆盖组 base 至最终 HEAD 的连续链.

  未处理项汇总后按 `KANDER-KANBAN-RULES.md`「契约与记录」以单行引用逐卡写入.

  主控按 `KANDER-TASK-GROUP-RULES.md`「组集成分支」集成.

  `develop` 前进引发的集成 rebase 按 `KANDER-TASK-GROUP-RULES.md`「合回与清理前置」处理; 已审核的 patch 必须原样保留, 主控不在组分支上解决任何冲突.

## 审核环节

除「审核档案」和白名单触发条件外, 每个角色是否运行还受默认环节策略约束.

配置文件的 `review_stages` 为四角色各指定 `auto`, `skip` 或 `required`, 缺省为 `auto`.

用命令根下的 `kander config` 查看.

解析每个角色时, 按优先级取第一个明确指定的来源:

1. 当前任务的用户指令.
2. 离目标文件最近的项目级 `AGENTS.md` 或 `CLAUDE.md`; 未指定时取用户自己的全局规则.
3. 配置文件中该角色的 `review_stages` 取值.
4. 审核档案与安全角色触发条件 (仅当第 3 档为 `auto` 时生效).

各档语义:

- `auto` — 按「审核档案」表和安全角色触发条件决定是否运行; 未触发时标 N/A.
- `skip` — 默认不运行并标 N/A, 除非更高优先级明确要求运行.
- `required` — 审核已触发时默认运行, 除非更高优先级明确要求跳过.

第 (2) 档写法示例: `本仓库 CSA 与 Hacker 一律 N/A`, 或 `本任务跳过 QA`. 被跳过的角色在交付说明记 N/A 并写明依据. 用户明确要求跑某被跳过角色时, 以用户指令为准.

## 审核档案

审核档案决定一轮审核里哪些角色运行, 以及各角色 review context「审核重点」的默认内容. 档案不改阶段顺序, 不改当前平台审核入口的调用方式和隔离参数.

- 档案由命中的白名单条目推导, 以任务实际改动为准.

  禁由执行 Agent 自行归类降级.

  命中多条时取并集: 各角色只启动一次首轮, 修复按增量复审处理.

  各条目侧重点合并到 review context 的「审核重点」.

- `PM` 与 `QA` 在审核档案中总是第一阶段并行的一对.

  是否实际运行仍受「审核环节」优先级链约束, 档案表只表达建议角色组合.

  `PM` 仅当命中条目全部标注"可免 PM"时才在 `auto` 模式下免跑, 免跑记 N/A 并写进交付说明.

- 安全角色触发条件 (`auto` 模式下): `CSA` 仅在改动涉及不可信输入, 认证授权, 凭据, 加密, 网络协议, 远程执行, 由不可信输入决定的文件写入, 安装更新或发布完整性时跑.

  `Hacker` 仅在新增或实质改变外部攻击面, 执行安全专项审核或用户明确要求时跑.

  档案表中的标注只是提示, 是否实际运行以安全角色触发条件与「审核环节」共同判定.

- 用户明确要求审核而未命中白名单时, 按用户指定的范围选档案; 未指定按功能开发档案跑全流程.

| 白名单条目           | 角色                 | 审核侧重点                                                           |
| -------------------- | -------------------- | -------------------------------------------------------------------- |
| 1 功能开发           | PM + QA              | PM 查需求完整性与流程闭环; QA 查回归与测试覆盖                       |
| 1 Bug 修复           | PM + QA              | PM 确认修复范围与根因一致, 无范围外改动; QA 查复现路径闭合与回归测试 |
| 2 超阈值代码修改     | 按内容归类           | 归入最接近的其他条目; 无明确类型时按功能开发档案                     |
| 3 安全敏感           | PM + CSA/Hacker + QA | `THREAT_MODEL` 必填不得写 N/A; 查隔离与权限边界, 凭据处理                   |
| 4 契约变更           | PM + QA              | PM 查影响面与文档同步; QA 查调用方适配与兼容处理                     |
| 5 不可逆或跨数据     | PM + QA              | 可逆性方案, dry-run 或等效证据, 失败中断后的状态                     |
| 6 构建安装发布门禁   | PM + QA (+CSA)       | 流程完整性, 升级与回滚路径; 涉发布完整性时触发 CSA                   |
| 7 依赖变更           | QA (+CSA); 可免 PM   | 来源可信, 版本锁定, license, 上游破坏性变更                          |
| 8 测试删除或放宽     | QA; 可免 PM          | 逐条核对删除或放宽的理由, 确认不是掩盖已知失败                       |
| 9 重构或公共模块删改 | QA; 可免 PM          | 行为等价性: 对外行为不变, 测试不改语义地全部通过                     |

## 主代理的核实义务

- 禁止不加核实就接受 reviewer 结论, 同样禁止不加核实就驳回.

  每条 finding 和每条 `NON-BLOCKING` 项都要主代理独立核实后才有处理结论.

  reviewer 的措辞, 语气, 自信程度和 finding 数量都不是证据.

- 核实必须回到目标 commit 的事实: 读相关代码与契约, 走通 finding 声称的触发路径, 需要时跑命令并记录输出. 只凭印象, reviewer 自述或"听起来合理"就下结论, 视为未核实.
- 核实结论只有三种:
  - **成立** — 按档位处理, 必修档修复并提交.
  - **不成立** — 不处理, 不修.

    常见类型: 依据与目标 commit 的实际代码不符.

    问题在 base 已存在且未被本轮加剧或掩盖.

    命中 task context`OUT_OF_SCOPE`的具体条目.

    超出契约, 即 finding 要求的行为既不在 `ACCEPTANCE_CRITERIA` 里, 也不是既有契约的逻辑必然 (并发交错, 跨平台或安全加固, 共享契约与架构文档同步都属此类, 除非验收条件点名).

    finding 假设的触发前提在本任务不成立.

    与另一条已受理 finding 同根因.

    超出契约项记入未处理项并建议后续卡, 不在本轮修.

    但本轮引入、加剧或掩盖的真实缺陷达到 `blocking` 或 `high` 时, 仍交用户决策是否纳入.

    未受本轮影响的既有问题仍按「目标与边界」排除.

  - **无法核实** — 说明缺哪项证据或环境, 交用户决策, 禁自行按不成立处理.
- 判为不成立或改档 (升档, 降档同理) 必须写明核实依据: 文件与行号, `commit` SHA, 实际跑过的命令与输出, 被引用的排除条目原文, 或引述用户明确决策及其时间.

  "影响不大", "以后再说", "改动太大", "reviewer 不懂上下文"一类无证据判断不算依据.

  降档后该项仍进未处理项清单.

- 全部不成立项与无法核实项进闭环结束时的未处理项清单, 交用户复核; 用户可推翻任一结论: 用户要求处理的项按必修处理, 用户拒绝处理的项以引述的决策为依据记为 `rejected`, 并保留在未处理项清单中.
- 认定成立不等于照抄 reviewer 给的修法: 主代理按最小正确修复执行. reviewer 的修法若会改变用户已明确的方向或对外契约, 按「目标与边界」交用户决策.
- 一个根因在派发摘要和面向用户的报告中只占一项: `PM` 与 `QA` 报告同一根因时, 只呈现和计数一次, 并引用两个来源 ID. 机器标识不合并: 每个 `(run_id, finding_id)` 在每个被归属任务上保留自己的处置, 重复项以另一项为依据. 禁在摘要中把一个根因按位置拆成多项, 或跨角色对同一缺陷重复计数.

## task context 与 review context 模板

- `OUT_OF_SCOPE`是审核的 risk-bounded stop 边界, 必须按四类逐一判定并写明理由:
  1. 改动前已存在的问题.
  2. 并发交错, 跨平台与安全加固.
  3. 共享契约, 公共 API 与架构文档的同步.
  4. 相邻功能与后续阶段.

  `ACCEPTANCE_CRITERIA` 未要求的类别写明排除, 由本卡承担的类别写明纳入.

  只有一条泛泛的排除不算契约完整, `pick` 前由建卡 Agent 补齐.

  审核时 reviewer 与主代理都以这份清单判定 finding 是否越出契约, 越出的记未处理项并建议后续卡.

task context 按以下六项组织; 均保留, 无适用内容写 `N/A`, 不补造 `USER_DECISIONS` 或 `ACCEPTANCE_CRITERIA`. 使用绝对 spec 时传完整契约, 包括已有的 `DISCUSSION`:

```text
GOAL: <改什么, 为什么改>
USER_DECISIONS: <用户已明确拍板的方向与取舍>
EXPECTED_OUTCOME: <完成后可观察, 可验证的状态>
ACCEPTANCE_CRITERIA: <逐项保留已确认的可验证条件>
THREAT_MODEL: <受保护资产, 可信主体与现实攻击者能力; 非安全任务写 N/A>
OUT_OF_SCOPE: <见下方清单, 逐条写明并附理由>
```

各阶段角色的可选 review context 用于证据和导航, 禁改 task context:

```text
本轮已含的修复: <前几轮认可 finding 的修复内容; 首轮省略>
审核重点: <(1)(2)(3) 分条, 指向本轮真正有风险的地方>
验证记录: <已跑过的命令与结果, 含未能执行的项及原因>
环境缺口: <影响验证的实际环境问题与替代证据; 没有则省略>
```

`OUT_OF_SCOPE`的具体边界让各角色 risk-bounded stop 生效, 避免把已知取舍或既有问题误报为本轮 finding. 常用条目:

- 非本轮引入的既有问题: `<具体项> 在改动前已存在 (见 <commit>), 修它等于扩大本任务范围.`
- 用户已明确拍板的方向或保留自决的区域: `这是用户明确要求的方向, 不要以 <相反主张> 为由反对方向本身; 用户已知悉相关取舍.`
- 契约之外的加固: `并发交错, 跨平台或安全加固未列入 ACCEPTANCE_CRITERIA; 本卡只保证 <ACCEPTANCE_CRITERIA>, 其余由 <后续卡> 处理.`
- 成本与收益不成比例的理论缺陷, 三条同时成立才可排除 (触发需额外前置条件已被攻破; 后果轻微或反而偏安全; 修复复杂度明显超收益): `<具体项> 的触发前提是 <前提>, 后果是 <后果>, 修复需 <成本>; 不属于本轮范围.`
- 环境导致的验证缺口: `<命令> 因 <原因> 未能执行, 已用 <替代验证> 覆盖; 不必据此判问题.`
- 项目已放弃向后兼容时: `项目已放弃全部向后兼容, 不要提兼容性, 迁移或 fallback 类问题.`

排除项只能排除"范围", 不能排除"严重级别": 禁写成"不要报 high"或"只报文档问题", 真实 blocking, high, medium 必须仍能报出.

排除理由必须落到事实 (哪个 commit 引入, 什么前提才触发, 用户哪句指示), 禁用"不重要", "以后再说"一类空话.

实现由其他 agent 完成时, 在 review context 说明并点出自己已修掉的问题, 让 reviewer 重点复查同类半改状态.

## 结论与故障处置

- 一次有效审核要求: 按「审核环节」实际运行的 `QA` 与 `PM` 没有未闭环的必修 finding: 每条 `blocking`, `high` 或 `medium` 项都已 `fixed` 并经验证, 或按「主代理的核实义务」以事实依据或用户决策原文 `rejected`.

  按触发条件实际运行的 `CSA`, `Hacker` 基于同一 commit 返回结论, 其安全 finding 已由用户决策或按超时规则记为超时忽略.

  `PM` 按档案或环节策略免跑时在交付说明记 N/A.

- 被判「无法核实」的 blocking, high, medium 视同未通过: 该阶段不得放行, 交用户决策. 用户判定为不必处理时, 将该决策引述为 `rejected` 处置的依据, 并把该项保留在未处理项清单中; 用户决定处理时, 按成立处理.

**未处理项汇总**

- 审核闭环结束时 (通过或中途终止), 必须向用户展示本轮全部未处理项, 一项都不省:
  - 未修的 `low`, `recommend`, `suggest`.
  - 被判定不成立或无法核实的 finding.
  - 用户已确认接受的风险, 超时忽略的安全 finding.
  - 因后端故障未完成的角色, 未提供 `NON-BLOCKING` 段的角色.
- 每项在用户报告中写明来源角色, 档位, 问题, 影响和理由.
- 交付说明以及看板任务的卡片按 `KANDER-KANBAN-RULES.md`「契约与记录」以单行引用承载同一批项目: finding 指向其处置记录; 未完成的角色, 缺失的段和验证缺口指向该运行的 sidecar 或错误日志, 档位与状态为 `N/A`, 或在没有运行时指向实际的命令日志或 `IMPLEMENTATION` 记录, 并注明"未产生运行". 全文保留在用户报告和审核产物中.
- 禁只报"审核通过"或"无阻塞问题".
- 未命中白名单跳过审核时按「前置条件与执行」的告知规则执行即可.

- 轮次上限: 同一 finding 经两轮修复仍未闭环, 或一个批次已跑三轮修复时, 停止. 向用户报告哪条 finding 卡住, 已试过什么, 并给编号选项 (`1. 接受当前状态并将该项记为未处理`, `2. 修改契约`, `3. 再继续一轮`). 不得自行开启下一轮.
- 审核入口参数, 认证, 前置条件或本地环境错误必须先修正.

  仅当参数与前置条件均正确的同一角色调用连续 3 次返回 HTTP 5xx 或明确 service unavailable 错误时, 视为该 reviewer 持续后端故障.

**第一阶段后端故障**

- `PM` 或 `QA` 持续后端故障时不自行换 reviewer: 保留分支和 worktree, 报告失败角色, 实际错误和已完成阶段, 停止集成, 等用户决定重试, 改期或明确指定另一个 reviewer.
- 提供换 reviewer 选项时必须按「Reviewer 选择」写明其限制: 该角色在批次内没有成功执行的运行时, 仅该角色用新 reviewer 重跑; 否则剩余选项是稍后重试或改期, 更换从下一批次起生效.
- 用户改的是整套 reviewer, 审核 base 或 task context 时, 才按对应规则作废全部阶段并从第一阶段重启 (`PM` 与 `QA` 基于同一 commit 并行首轮).

- `CSA` 或 `Hacker` 持续后端故障不阻塞第二阶段决策, 但在批次要求中记为 `required` 的角色在批次关闭前仍需要一次成功运行: 该角色记为"因后端故障未完成", 在交付说明和汇报里写明, 语义结论由 `PM` 与 `QA` 决定, 并按「Reviewer 选择」等待用户重试, 改期或更换 reviewer. 只有在批次要求中记为 N/A 的角色不需要运行.

  两个安全角色都触发时其中一个故障, 另一个照常出结论并按第二阶段规则处理.

## 受控计划, 作者处置与批次关闭

- 完成活动卡片前, 先用 `kander review plan <CWD> <absolute-plan.json>` 建立机器可读的执行审核计划. 计划列出周期, 作者与依据, worktree, 语言, 成员, 有序的批次 ID, 每个批次的 base/target, 以及全部四个角色的要求. 按既有优先级解析后取 `required` 或 `N/A: <reason and applicable rule basis>`. 禁用或不适用的审核需要显式 N/A 记录; 空索引绝不意味着豁免. 已完成的历史卡片可保持 `legacy-untracked`, 不伪造过去的 PASS.
- 单个已知批次可用封存的计划. 增量安排批次时, 待每个成员都已进入 `working/` 或 `review/` 且在首批运行前创建未封存计划, 以其 base 和当前目标命名该批次, 再在前一批关闭后、该批首次运行前用带预期计划 revision 的 `review extend-plan <CWD> <absolute-request.json>` 追加每个后续批次 (`KANDER-KANBAN-RULES.md`「审核证据完成门禁」). 保留既有批次, 要求和成员. 只在每个成员都已分配后封存. 未封存的计划和未关闭的批次阻止 done. 绝不通过替换计划来丢弃失败的运行. 成员在创建计划时固定: extend-plan 只追加批次或封存, 绝不增删成员, 已在 `done/` 或 `archived/` 的成员不能被扩展. reclaim 引起的周期变更按 `KANDER-KANBAN-RULES.md`「审核证据完成门禁」重新绑定. 禁同周期重置. advance 与 extend-plan 必须使用计划的确切 CWD.
- 新报告必须恰好包含一个 `kander-findings` 围栏 JSON 对象, 带必填的 `FINDINGS` 和 `NON_BLOCKING` 数组. 每项含 `id`, `tier`, `text` 和 `evidence`; ID 在两个数组中唯一. 门禁档位只属于 FINDINGS, low/recommend/suggest 只属于 NON_BLOCKING. 空数组明确表示无项目. 普通叙述中的引用不算条目. ID 缺失/重复, JSON 键重复, 结构无效和空的作者处置都不能免除覆盖.
- finding 的标识为 `(run_id, finding_id)`. 增量沿用的项目用显式 `lineage: {run_id, finding_id}` 指向直接前驱中的实际项目. 保持 ID 稳定, 在结构化块中报告完整项目.
- 旧的非结构化报告保留原件. 要使用它们, 通过 `review map-legacy <CWD> <absolute-map.json>` 提交显式完整的人工映射, 含作者, 依据, 原始报告哈希, 结构化项目, 以及确切的原文行范围与引文. 映射发布同样先校验 lineage; 无效的映射请求被拒绝且不创建不可变映射, 可修正后重新提交. 缺少 ID 搜索或空映射不是无 finding 的证据. 新 schema 的报告不能走该兼容路径; 须获取有效的新报告.
- 通过 `review assign <CWD> <absolute-assignment.json>` 归属每个项目, 带 run/批次, 归属作者与依据, 以及显式的项目到任务数组. 跨卡 finding 要求列出每个实际负责人. 空归属仅对已解析且无项目的报告有效.
- 每个执行 Agent 在工作期间通过 `review disposition <CWD> <absolute-record.json> <expected-card-revision>` 独立核实并只提交自己被归属的 finding. 绑定记录/run/finding/批次/任务 ID, 作者, 原始报告哈希与项目文本, 状态, 事实依据, 以及适用的修复 SHA 与验证. 工具记录时间. 修订以新记录 ID 追加并引用前一条记录, 保留原作者文本. 后继 OWNER 可在同一被归属任务上追加自己独立核实的结论. 工具把每条新记录绑定到当前工作中的 OWNER 与卡片 revision; 原归属的所有权和所有前作者的记录保持不变. 交接后前任负责人不能提交. 主控绝不得冒充执行作者或覆盖这些记录.
- 必修项状态为 confirmed/fixed/rejected/unverifiable/waived; `deferred` 对必修项无效. confirmed 与 unverifiable 项阻止关闭; rejected 项需要事实证据或用户决策原文, 并保留在最终未处理项清单中. fixed 项绑定后续修复 commit 与实际验证. 非阻塞项状态为 fixed/deferred/rejected, 均须附依据, 且关闭同样要求每个被归属的非阻塞项都有处置. 委托占位无效.
- waived 仅限既有的 CSA/Hacker 接受风险或看板超时规则. 记录适用的策略与用户的实际决策, 或完整的通知依据以及相隔至少 15 分钟的发送/超时时间. 豁免不是 PASS. PM/QA 必修项, 无法核实项, 以及验收/集成授权不能使用该例外; 用户对这些项的决策按「主代理的核实义务」以引述的决策记为 `rejected`.
- `review aggregate <CWD> <batch-id>` 校验全部运行发布与作者原件, 对 run ID 去重, 并向每个成员发布生成的处置视图. 保留作者措辞与署名. 无 finding 的成员不需要仅为复制结论而通知. 主控可在关闭请求中加入单独署名的核实意见; 这些不替代作者处置.
- 纯机械修复用 `review advance <CWD> <absolute-request.json>` 对既有批次目标做 CAS, 不启动 reviewer. 提供批次 ID, 预期 revision, 以及带每次批内交付的既有推进契约. 目标处 worktree 必须干净. 保留机械类别 (documentation/dead-code/redundant-test), 修复 SHA 与实际验证. 仅凭处置的机械标签不能推进 PASSED_AT. 关闭的主代理必须为每个例外提供单独的 `mechanical` 评估, 绑定到确切的 run/finding/任务/作者记录, 报告哈希, 修复 SHA, reviewer 类别 (含无标签), 实际验证事实以及改动路径及其 Git diff 哈希. 工具把该范围绑定到 Git 证据; 主代理仍要核实机械定义与事实结论. 缺失的 reviewer 标签可在独立核实后归类; 既有标签不是证据. 只有这些允许的修复可以不新跑角色而推进 PASSED_AT. 非机械必修项要求后续审核覆盖修复 commit.
- 增量 `review --task ... --previous-run-id ...` 自动加载上一份报告和作者记录, 以及生成的批次视图. 手动上下文在单独的补充段中逐字保留, 不替代原件; reviewed-commit 按「调用参数」. 上一轮的语义结论可以是 FAIL. 证据缺失, 不一致, 属于外部成员, 语言错误或轮次错误时在启动 reviewer 前拒绝; 重试保留原始冻结输入, 补充文本有变动即拒绝.
- 仅在每个必需角色都有有效结论后才通过 `review close <CWD> <absolute-request.json>` 关闭. 绑定批次 ID, 预期 revision, 确切 aggregate JSON 输出的 SHA-256, 选定的角色 run ID, PASSED_AT 与核实依据. 显式把所有失败尝试关联到其成功的替代. 失败的执行绝不是 PASS, 一个成功的角色不能顶替缺失的角色.
- 关闭时校验实际的最终干净 HEAD, 以及 base, 通过 commit, 修复与目标之间的 Git 关系. 它连同完整处置发布最终目标与确切的已核实证据. 部分发布不是关闭. 已关闭的批次不接受新运行, 目标推进或作者变更. 下一批次指明上一个已关闭批次并以其最终目标为 base, 绝不用任意较早角色的通过或墙上时钟顺序.
- `check` 与 `move done` 共用结构化证据校验. 待定的作者结论是正当的执行进度; 已有证据格式错误则是错误. 结构化校验绝不断言代码已集成. 既有的集成授权, 交付检查, rebase 处理和最终 Git 校验仍然强制.

全部四个角色都显式 N/A 的非 Git 工作流中, base 与 target_commit 可同为 N/A. 关闭记录 Git 为不适用, 而不是伪造祖先证据. 必需的审核角色始终要求真实的 commit 目标.
